# Practical teaching specification

Version1.1. November14,2026.

## Teach someone through the work

Write for a beginner or fresher who can use an application and has basic account knowledge. Use the patient, polite mentor voice established in the theory course. Keep the English clear for a reader who uses it as an additional language.

Explain the practical purpose before the action becomes a list of settings. Show what exists now, what the learner needs to change or establish, which actor performs the action, why that action helps and what result to inspect.

Use real ISC terms and explain them in context. A source, identity, account, review item, manager correlation, sign-off or remediation must have a useful meaning before the instruction relies on it. Tooltips or theory links cannot carry an essential explanation.

No fictional company, continuing character, biography, course-design commentary, abstract opening, congratulatory filler or unexplained technical sentence chain.

## A practical step needs a checkable result

An instruction should connect the action with its purpose and a visible observation. Use the exact inspected route, field name or supported operation for the recorded environment. Explain harmless wording differences by identifying the underlying object or result; do not guess a button when the interface differs.

Separate what the learner should expect from what was actually observed during author validation. Do not fabricate a passing result, screenshot, runtime delay or tenant capability. An accepted request may still need an operation-state check and an actual account observation.

When the result differs, provide a useful first investigation based on the affected record. Avoid an exhaustive diagnostic tree at every step. The relevant troubleshooting lab owns deeper variations.

Documented backend explanations concern supported relationships and processing. Do not invent internal queues, database tables or a universal action order.

## Entry conditions and independence

Every lab names its task, necessary permission/capability, exact starting inventory and a way to establish or restore it. These are operational facts the reader needs, not an announcement that the lesson is independent.

The learner can use a verified shared seed package, but the lab must identify its version, expected holdings, actual required actor and reset. No hidden dependence on the outcome of a previous run.

Do not require all61 theory lessons before a learner can attempt setup. Explain the local meanings and direct them to the actual requirement. Do not add course/source links to learner prose.

## Keep the structure dynamic

Use the amount of explanation, diagrams, screenshots, tables and exercises the task needs. There is no fixed module count, word count or identical set of headings.

A normal review, a source-data repair and an API investigation need different presentation. Do not turn each theory term into a lab. A later lab should add a distinct practical decision, task or verification.

Keep the ordinary complete path understandable before introducing a changed condition. Place a qualification next to the action it affects without turning every step into an exception catalogue.

## Evidence and screenshots

Use screenshots from actual authorized course runs. The image should reveal the relevant choice or result, with enough prose to understand it without the image. Redact unrelated identities and sensitive details before reusable publication.

A screenshot of a success message is evidence of that message. It is not automatically evidence of an external account change. Match person, source, account, right, operation/task and times.

The initial setup uses fresh CSV sources. Label the external file edit as a simulation while treating observed ISC review/task work as actual ISC work. Never claim an automated real-account change from a CSV refresh. The connected extension has its own target evidence.

Keep both required removals and approved retained access in the result check. Refreshing an ISC collection or regenerating a report has a different purpose from inspecting the current application account.

Source links, exact documentation checks, engine/feature limitations and validation metadata belong in author records, not as citation clutter inside the learner's instructions.

## Practice and independent explanation

Ask the learner to predict an outcome or justify a choice when that reveals understanding. Supply the needed facts and supporting meanings before the question.

A worked answer explains the reason and the relevant evidence. Separate it from the attempt; choose a simple format suited to the reader used at publication. A later exercise must not require opening an earlier hidden answer to find a necessary fact.

The independent capstone should provide a usable environment and evidence, then ask the learner to choose and defend their own approach. Do not call a copied sequence an uncoached pass.

## Changes and reset

A mutating exercise names the isolated test boundary, actual authorized actor and exact affected objects. Limit changes to that boundary. Inspect the starting state before the first mutation.

Explain the reset as carefully as the forward operation. Record outstanding work, evidence preservation, the supported restoration action and the result needed before another run. Never use campaign deletion as an assumed cancellation, access restoration or rollback mechanism.

A missing prerequisite affects that lab's execution state. Continue independent design or another ready lab; do not invent a result or mark unavailable functionality passed.

## Completion states

Authored: the complete learner instructions and explanation exist.

Author-reviewed: the saved file has been fully read for beginner clarity, local meanings, causal steps, source support, input/output consistency and reset.

Executed: a named actor performed the actual lab in the recorded training setup and retained results.

Repeated: the lab was reset and successfully run again from its stated baseline.

Learner-tested: an actual learner completed the specified task without hidden author coaching, with recorded evidence.

Published: a specific revision was delivered to the stated repository/site.

These are independent facts. Website checks do not constitute ISC execution. A reported available tenant is not a verified lab environment.

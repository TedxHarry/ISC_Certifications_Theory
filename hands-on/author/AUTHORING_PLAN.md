## Delivery approach

Build one complete learner file at a time. Keep the initial normal review reachable, preserve the23-unit planning inventory without treating it as a quota, and validate only the specific environment actually used.

Plain Markdown is the initial format. Real screenshots and import files are added when their source environment and schema exist. A future repository/reader is separate work.

## File responsibilities

COURSE_DESIGN.md owns the initial outcomes, practical inventory, route choices and24-family mapping. COURSE_REGISTER.md owns actual writing/review/execution/publication status and the next unit.

TEACHING_SPECIFICATION.md owns the clear practical explanations and evidence/reset standards. LAB_ENVIRONMENT.md owns reported versus inspected environment facts. lab-data/BASELINE_SPECIFICATION.md owns the complete proposed first fixture and its expected holdings.

[CSV_LAB_STRATEGY.md](../CSV_LAB_STRATEGY.md) owns the selected fresh-file setup and the boundary between actual ISC work, simulated external changes and later connected outcomes.

The source register and each per-lab author record own technical checks and execution limits. Briefs establish distinct job, inputs, task, meaningful changed condition and proof before learner prose.

## Review focus

Can a beginner name what a step reads or changes and why? Does the expected item/account set reconcile with the baseline? Does an unfamiliar supporting term have a local meaning before the action uses it?

Can the actual reviewer sign in and see the right work? Does the target prove both removal and retained access? Is a manual task's actual recipient known? Is accepted versus completed processing checked without an invented delay?

Can the lab be reset without touching other work, losing evidence or racing outstanding operations? Does the result distinguish authored instructions, documentation support, execution, repetition and learner performance?
